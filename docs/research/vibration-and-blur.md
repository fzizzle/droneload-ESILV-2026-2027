# Widen the gate, then shorten the exposure

The largest and cheapest gain is in the team's own tracker, not in a new algorithm. `MAX_JUMP_PX = 40` is smaller than the 43 px mean frame-to-frame move under simulated moderate shake, so the tracker throws away about half of the markers the detector still finds (**raw 63.8% → tracked 32.6%**). ArUco IDs are unique, so that gate does no association work. It only guards against rare false decodes. A gate that scales with marker size, or one that runs after camera-motion compensation, should recover most of the gap at no hardware cost. The second cheap lever is a code fact. With `DICT_4X4_50` and OpenCV's default `errorCorrectionRate = 0.6`, the detector computes `int(1 × 0.6) = 0` and **corrects no bit errors at all**, so one bit flipped by blur rejects the marker. After those two fixes, the physics takes over. Blur in pixels equals angular rate × exposure × focal length, and standard ArUco holds full detection only while blur stays under about 10% of the marker's width. Short fixed exposures (roughly 1-4 ms), a global-shutter mono sensor, fixed focus and a properly damped mount are therefore the high-value hardware moves. Learned detectors and deblurring networks roughly double recall in published tests, but every published timing comes from a desktop GPU, so their speed on the Qualcomm companion is **unverified**. One caveat shapes all the testing. The main benchmark runs on Shadow-ArUco footage with `DICT_ARUCO_MIP_36h12`, and the real-footage vibration run uses `DICT_ARUCO_ORIGINAL`. Neither measures the contest dictionary, so some of the changes below need a `DICT_4X4_50` test set before anyone can judge them.

## The 40 px gate discards half of what the detector finds

> **Status, 2026-11-16: done (PR #24).** The gate is now max(20 px, 0.75 × marker side) × frames since last seen. At fdcl-gwu moderate, tracked rose from 32.6% to 54.1% with 0.1 false IDs per 100 frames. Camera-motion compensation was prototyped and not kept: no gain on simulated shake, more false IDs, 5.7 ms per frame. See `droneload/vision/tracking/README.md`.

The tracker in `droneload/vision/tracking/tracker.py` accepts a detection only if it lies within `MAX_JUMP_PX × since_hit` of the marker's last detected position. A confirmed track counts a far detection as a miss, and a marker is reported only after 3 hits in a 5-frame window. When the mean move is 43 px, a 40 px radius rejects roughly half of the true detections. Those misses then stop tracks from confirming, which matches the drop from 63.8% to 32.6%. Multi-object trackers avoid this failure by design. DeepSORT gates on the Mahalanobis distance from a Kalman-predicted position, **thresholded at the 95% chi-square value (9.4877 for a 4-D measurement)**, and keeps new tracks "tentative during their first three frames" ([DeepSORT](https://arxiv.org/html/1703.07402v1)). BoT-SORT makes the Kalman noise **proportional to object size (σ = 0.05 × width)**, so the gate grows with the apparent size of the object ([BoT-SORT](https://arxiv.org/pdf/2206.14651)). Both also have to assign detections to tracks, which is the job their gates exist to protect. Here the ArUco ID does the assignment. The gate only has to catch a wrong ID decoded in the wrong place, so it can be loose. The cheapest experiment is to sweep the gate at 40, 80 and 120 px and with no gate at all, then replace it with a multiple of the marker's side length. The vibration test already prints false IDs per 100 frames next to the tracked rate, so the experiment shows directly how much recall the gate costs and how many false IDs it actually blocks.

A Kalman filter on its own will not fix shake. Vibration oscillates around zero, so a constant-velocity prediction overshoots after every reversal. The more useful step is to remove the camera's own motion before gating. BoT-SORT's camera-motion compensation tracks background keypoints with sparse optical flow, fits an affine transform with RANSAC, and warps each track's prediction into the new frame. The authors say this matters even for static cameras that move "by vibrations or drifts caused by the wind". On MOT17 it gave the largest single gain in their ablation, with **IDF1 rising from 79.89 to 81.51** ([BoT-SORT](https://arxiv.org/pdf/2206.14651)). MOT17's camera motion is slow, so the gain under high-frequency shake is probably larger, though no source tested that. The whole pipeline uses OpenCV functions the project already has: `goodFeaturesToTrack` with the marker quads masked out, pyramidal `calcOpticalFlowPyrLK`, and `estimateAffinePartial2D`. It needs no new dependency, and its cost on the Qualcomm board is **unverified**. The vibration test applies a global affine shake, so compensation should recover most of the gap there. Real flights add rolling-shutter wobble and parallax, and a textureless arena floor may give KLT too few features. In that case the fallback is the motion implied by the markers themselves.

Two smaller issues sit in the same file. First, `SMOOTHING = 0.6` blends each logged position with the previous one. For a 43 px move, that leaves the logged centre about 17 px behind the detection. That is an inference from the formula, and neither test measures position under shake: the vibration test scores IDs only. Causal smoothers always trade jitter for lag. The 1€ filter reduces lag during fast motion ([Casiez et al.](https://cristal.univ-lille.fr/~casiez/1euro)), but the clean answer for logs that must be unbiased is to log raw detections and smooth offline if smoothing is ever needed. Second, markers lost in single blurred frames can be recovered by re-running `detectMarkers` on an upscaled crop around the compensated prediction. That gives a real detection rather than an extrapolation. Filling gaps with KLT-propagated corners is also possible, but those positions are estimates. They need a provenance flag, and adding a column changes the CSV format. `refineDetectedMarkers` needs a known board layout, so it does not help isolated markers ([OpenCV RefineParameters](https://docs.opencv.org/4.x/d5/d09/structcv_1_1aruco_1_1RefineParameters.html)). The ArUco library's correlation-filter tracker was built for exactly this problem and claims over 200 fps on HD images ([Romero-Ramirez et al. 2021](https://burjcdigital.urjc.es/handle/10115/42238)), but it is a separate C++ library, reportedly GPL, with Python bindings **unverified**.

## DICT_4X4_50 currently corrects zero bit errors

OpenCV builds `DICT_4X4_50` with `maxCorrectionBits = 1`. `Dictionary::identify` accepts a code only if its Hamming distance is at most `int(maxCorrectionBits × errorCorrectionRate)`. At the default rate of 0.6 that is `int(0.6) = 0`, so **only exact matches pass, and any value from 0.0 to 0.99 behaves the same** ([OpenCV aruco_dictionary.cpp](https://raw.githubusercontent.com/opencv/opencv/4.x/modules/objdetect/src/aruco/aruco_dictionary.cpp)). `make_detector` in `detect.py` does not set this parameter, so the contest pipeline has no tolerance for a bit flipped by blur. Setting it to 1.0 enables 1-bit correction, and the cost is false positives. On 15,620 marker-free images, 4X4_50 at full correction produced **2,349 false positives, against 269 for 5X5_50 and 785 for ARUCO_ORIGINAL**, and it had the worst validation-failure probability of every library tested ([STag](https://arxiv.org/pdf/1707.06292)). The DeepArUco++ authors built their ground truth by setting correction to zero precisely because "this weeds out most false detections" ([DeepArUco++](https://arxiv.org/pdf/2411.05552)). Two controls make the change safer. The team uses only IDs 0-9, so any decoded ID from 10 to 49 is by definition a false positive. `detect.py` currently logs those IDs with an `unknown_N` label instead of dropping them. Further, a custom dictionary holding only the first ten 4X4_50 codes would keep the same bit patterns but offer fewer codes to match by chance. That counts as a dictionary change and needs a team decision. Whether those ten codes sit further apart than the full set's minimum distance was not checked.

The other detector parameters offer smaller gains, and none has a published sweep against blur, so every value below is a hypothesis for the benchmark. The current detector already widens the threshold windows (3-53 in steps of 10), lowers `minMarkerPerimeterRate` to 0.02 and raises `polygonalApproxAccuracyRate` to 0.05, which the research independently suggested for rounded, blurred quads. The untouched levers are bit sampling and threshold contrast. Raising `perspectiveRemoveIgnoredMarginPerCell` from 0.13 to 0.2-0.3 samples cell centres, where bleed from neighbouring cells is weakest. Raising `perspectiveRemovePixelPerCell` from 4 to about 8 gives those centres more samples, and OpenCV says a higher value "can improve the bits extraction process (up to some degree)" ([OpenCV ArUco tutorial](https://raw.githubusercontent.com/opencv/opencv/4.x/doc/tutorials/objdetect/aruco_detection/aruco_detection.markdown)). Lowering `adaptiveThreshConstant` from 7 helps low-contrast edges survive binarisation, but it adds candidates. Corner refinement does not change which markers are found, with one exception: `CORNER_REFINE_APRILTAG` replaces candidate detection with the AprilTag 2 method, so it is worth one test ([OpenCV aruco_detector.hpp](https://raw.githubusercontent.com/opencv/opencv/4.x/modules/objdetect/include/opencv2/objdetect/aruco_detector.hpp)). `useAruco3Detection` is a speed tool, reported "up to 40 times faster" ([URJC](https://burjcdigital.urjc.es/handle/10115/42233)). Its value here is the CPU time it frees for more threshold scales or ROI re-detection. The CLAHE step in `preprocess` addresses lighting, not blur, and it can amplify noise. Run it on and off on shaken footage. Unsharp masking and sharpness-based frame gating have no published ArUco evidence either way.

The test harness limits what these experiments can show. The benchmark footage is Shadow-ArUco, the dataset on which **classic ArUco matched 53.3% of markers** in the DeepArUco++ paper ([DeepArUco++](https://arxiv.org/pdf/2411.05552)). The team's 56.4% is therefore about what the literature predicts, but that dataset tests shadows and moving light patterns, not blur. It also uses `DICT_ARUCO_MIP_36h12`, whose correction capacity differs from 4X4_50, so an `errorCorrectionRate` change measured there says little about the contest markers. The real-footage vibration run uses `DICT_ARUCO_ORIGINAL`, which has zero correction bits, so the change does nothing there. The synthetic marker sweep in `testing/vibration_test.py` (run without `--source`) does use `DICT_4X4_50`, and it is the only existing 4X4_50 measurement. Printed contest markers filmed on a hand-shaken phone would be a better one.

## Exposure sets the blur budget, and the shutter sets the jello

Rotational blur in pixels is approximately **ω × t × f_px** ([US 7509038](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7509038)), and machine-vision practice treats anything past about 1 px as blur ([1stVision](https://www.1stvision.com/machine-vision-solutions/?p=946)). The tolerance that matters comes from the ArUco authors' synthetic tests. Standard markers sustained **100% detection up to blur of 10% of marker width**, because "their bits are physically larger" than those of nested designs ([Recursive ArUco](https://arxiv.org/pdf/2607.13830)). A 4x4 marker with a one-cell border is 6 cells across, so the rule works out to blur below about 0.6 of a bit cell. Take a 1280 px sensor with a 70° lens (f ≈ 914 px). A 100°/s correction then blurs 13 px at an 8 ms exposure. A 60 px marker tolerates only about 6 px, which caps the exposure near **3.8 ms**, or about 12.6 ms at 30°/s. These figures are the research team's arithmetic, not measurements. Marker size and blur both scale with focal length, so their ratio does not depend on the lens when rotation dominates. Focal length sets range and pixels on the marker, and exposure alone sets the blur ratio. Real motion is harsh. In a servo-driven moving-camera test, **ArUco detection fell to 64%, 50% and 43% at 50, 100 and 150 cm** ([U.P.B. Sci. Bull. 2023](https://www.scientificbulletin.upb.ro/static/pdfs/full7bc_966141.pdf)). The team's numbers look typical rather than a bug.

Short exposures conflict with the arena lighting. In France, mains lighting flickers at 100 Hz, and the flicker-safe exposures of 10 or 20 ms ([Vadzo](https://www.newswire.com/news/vadzo-imaging-explains-led-flicker-mitigation-techniques-for-22791982)) blur far too much. At 1-4 ms, expect frame-to-frame brightness changes with a global shutter, or horizontal banding with a rolling one. The adaptive threshold absorbs some of this, and a DC-powered LED ring on the drone would remove it, but that is a hardware choice. Whether the arena lights flicker at all is unknown. A slow-motion phone video would answer it.

Rolling shutter is the second hardware problem. A typical rolling sensor reads a frame in about 16 ms (DJI Mavic 3, measured from light banding ([Pix-Pro](https://www.pix-pro.com/blog/dji-mavic-3-rolling-shutter))). ArduPilot puts the motor vibration peak at about 100 Hz on larger copters and 200 Hz on smaller ones ([ArduPilot IMU batch sampling](https://ardupilot.org/copter/docs/common-imu-batchsampling.html)). That is a 5-10 ms period, so each frame spans one or more vibration cycles and square markers bend into waves. The project's own simulation already found that wobble hurts more than blur. Every camera the Rubik Pi 3 manual supports, **IMX477, IMX219 and IMX708, is rolling-shutter**, and IMX708 autofocus is unsupported ([Thundercomm](https://www.thundercomm.com/rubik-pi-3/en/docs/rubik-pi-3-user-manual/1.0.0-u/peripherals-and-interfaces/csi)). Global-shutter options include the OV9281 (1 MP mono, about US$26 at Arducam), the Sony IMX296 (1.6 MP, Raspberry Pi Global Shutter Camera, about £38 ex VAT at Farnell) and the onsemi AR0234 (2.3 MP, about US$100 as a TechNexion module) ([Arducam OV9281 docs](https://docs.arducam.com/Raspberry-Pi-Camera/Native-camera/Global-Shutter/1MP-OV9281-OV9282/); [Farnell](https://uk.farnell.com/raspberry-pi/sc0926/global-shutter-camera-computer/dp/4163984); [TechNexion](https://www.technexion.com/shop/embedded-vision/mipi-csi2/tevs/tevs-ar0234-c/)). Prices are snapshots of unknown date. None is confirmed on the Qualcomm camera stack. RidgeRun has shown a third-party sensor driver running through `qtiqmmfsrc` on the Rubik Pi 3 ([RidgeRun](https://developer.ridgerun.com/wiki/index.php/Mira220_Camera_Driver_for_Rubik_Pi_3)), so driver work is possible, and a USB UVC global-shutter camera would bypass that stack entirely. Both routes are **unverified** on the organisers' board, whose exact model is itself unconfirmed. A mono sensor suits ArUco, which works in greyscale. Luxonis advises fixed focus on drones because a voice-coil autofocus lens "vibrates all over the place" ([Luxonis](https://docs.luxonis.com/hardware/platform/sensors/focus-type)).

Mechanical fixes come before any of this. ArduPilot and PX4 both say to remove vibration at its source first: balanced props, concentric adapters, tight arms and flexible wiring. Then isolate the camera, with Kyosho Zeal gel rated best of the materials ArduPilot lists, and avoid over-soft mounts that resonate ([ArduPilot vibration damping](https://ardupilot.org/copter/docs/common-vibration-damping.html); [PX4](https://docs.px4.io/main/en/assembly/vibration_isolation)). Textbook isolation theory suggests a mount resonance of about 20-40 Hz to attenuate a 100-200 Hz prop band, which is an inference that needs measuring. The Pixhawk's VIBE log should read **below 15 m/s² with zero clipping** ([ArduPilot measuring vibration](https://ardupilot.org/copter/docs/common-measuring-vibration.html)). VIBE measures the flight controller, not the camera bracket, so marker-corner jitter in the images is the check that matters. A brushless gimbal (about 170-200 g) mainly removes slow attitude motion, not prop vibration. For a fixed short-exposure camera, it probably costs more in mass and failure modes than it returns.

## Learned methods double recall, but nobody has timed them on Qualcomm

The learned results are large and consistent. On Shadow-ArUco, the team's own benchmark dataset, **DeepArUco++ matched 95.1% of markers against 53.3% for classic ArUco**. Classic ArUco kept the best precision and corner error (0.72 px), and the learned pipeline took 26.9-29.9 ms per frame on an RTX 3090 ([DeepArUco++](https://arxiv.org/pdf/2411.05552)). Under synthetic horizontal blur, OpenCV fell to **0% at kernels of 6 px or more** while Deep ChArUco held about 94%. On real motion sequences the split was 78% good poses against 27%, though its learned corner refiner made blurred corners worse ([Deep ChArUco](https://arxiv.org/html/1812.03247v2)). Deblurring before detection also works when trained on marker imagery. Ghost-DeblurGAN raised AprilTag-plus-ArUco detections on blurred YorkTag images **from 32% to 59%**, at 37 ms per frame on a Quadro RTX 4000 ([Ghost-DeblurGAN](https://arxiv.org/pdf/2109.03379)). SlimDeblurGAN raised landing-pad F1 on real blurred drone frames from 0.487 to 0.606 at 18.3 ms on a Jetson TX2, but generic deblurrers **lowered** F1 on synthetic blur ([SlimDeblurGAN](https://pmc.ncbi.nlm.nih.gov/articles/PMC7411990/)). A network not trained on markers can make detection worse.

Embedded speed is the open question. A full NAFNet takes 177 ms on a Galaxy S24 Ultra NPU ([Samsung, arXiv 2601.11685](https://arxiv.org/pdf/2601.11685)). Qualcomm lists tiny INT8 restoration networks at about 1 ms and YOLOv8 detection at about 3.6-4.7 ms on the QCS6490 NPU ([Qualcomm XLSR card](https://huggingface.co/qualcomm/XLSR-Quantized); [Qualcomm YOLOv8](https://huggingface.co/qualcomm/YOLOv8-Detection)). These are vendor figures, **unverified**, for a chip that may not be the organisers' chip. The plausible design is a hybrid. A small YOLO proposer, trained with blur augmentation, finds marker regions, and classic ArUco decodes the crops, which keeps ArUco's precision. No published detector has been trained on 4X4_50, however, so it means new dependencies, training data and an NPU toolchain.

The remaining options have weak evidence. No study shows Wiener or Richardson-Lucy deconvolution raising fiducial detection rates. Both are non-blind and "introduce undesirable ringing artifacts" ([Optik 2020](https://www.sciencedirect.com/science/article/abs/pii/S0030402620307385)), and ringing near cell edges is exactly what flips ArUco bits. No study shows electronic stabilisation raising detection either, and warping before detection moves the pixel coordinates the team logs. Gyro fusion is well established for feature tracking, but Poling and Lerman found gyro-predicted initialisation gave **no clear advantage over careful optical-only initialisation** ([arXiv 1511.01508](https://ar5iv.arxiv.org/html/1511.01508)). The sync burden is severe. A 10 ms timing error during a 5 rad/s shake at f ≈ 600 px is about 30 px, as large as the shake itself. PX4 users also report getting only 185-189 Hz when requesting 200 Hz HIGHRES_IMU over MAVLink ([PX4 forum](https://discuss.px4.io/t/increase-stream-rate-of-highres-imu-message/4789)). CCTag circles beat ArUco under motion in the servo test (74.6% against 64.4% at 50 cm) ([U.P.B. Sci. Bull. 2023](https://www.scientificbulletin.upb.ro/static/pdfs/full7bc_966141.pdf)), but switching marker systems is probably not the team's call to make.

## What to try, in order

The order puts no-dependency code changes first, test-harness work second because it decides what can be measured, and hardware or decision-gated items last. "Decision" means a person must approve it under `AGENTS.md` before anyone starts. Every detection change also needs `./scripts/check.sh`, a new test in `tests/`, and `python -m testing.benchmark` before and after (baseline found=56.4%, unmatched=26.6%). Shake-related changes also need the fdcl-gwu vibration run before and after (baseline at moderate: raw=63.8%, tracked=32.6%). Camera and mount items count as tested only on the real hardware.

## Conclusion

The team's 56.4% benchmark figure is not a sign of a broken detector. It sits almost exactly on the published classic-ArUco result for the same dataset, which means more tuning of the same detector has a low ceiling. The real headroom is upstream and downstream of the detector. Upstream, short exposure and a global shutter keep blur under a fraction of a bit cell. Downstream, a tracker that trusts unique IDs and compensates for camera motion stops discarding good detections. The first improvement is therefore a constant and a gate formula, not a new camera, and it can be measured this week with the vibration test.

The deeper finding is that the measurement setup must change before the detector can. The two baselines test a dictionary and a lighting problem that differ from the contest's, so a `DICT_4X4_50` shake set is a prerequisite for judging error correction or bit-sampling changes honestly. Building that set first is the step most likely to stop the team from optimising for the wrong footage.
