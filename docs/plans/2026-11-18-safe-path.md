# Safe Path Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Needs the project lead's OK before Task 2:** from there on, this code steers a simulated drone (`AGENTS.md`, Stop and Ask).

**Goal:** Follow the safe path from zone A to zone C and back with the downward camera. With take-off and a landing on ArUco 0 this is Part 2 flown automatically: 110 points, and the crossing half of Mission 1.

**Architecture:** `vision/lines.py` finds the green and yellow lines by colour and reports where the path's centre is in the image and which way it runs. `navigation/path.py` turns that into a forward speed, a sideways correction and a yaw rate. The colours give the direction for free: outbound the green line is on the drone's right, and on the way back it is on the left.

**Tech Stack:** OpenCV, numpy, pytest. No new dependency. Tests draw a path on a `testing.sim_camera` floor.

**Spec:** `docs/contest-rules.md`, Arena (zone D) and Flight Test; `droneload/navigation/README.md` ("Follow a 5 m taped path both ways without leaving it").

## Global Constraints

- Needs these plans merged: `sim-camera`, `flight-velocity`, `mission-runner`, `centre-and-land`.
- **Unknown until the organisers answer:** the line width, the gap between the two lines, the exact colours and what marks each end. Each is a constant at the top of its file, set to a labelled guess: `LINE_GAP_M = 1.0`, line width 5 cm in tests.
- Colour ranges are HSV constants at the top of `lines.py`: `GREEN_HSV = ((40, 70, 60), (85, 255, 255))`, `YELLOW_HSV = ((20, 90, 90), (35, 255, 255))`. They must be retuned at the venue; Task 4 adds the tool for that.
- The camera must be in colour. `camera_picamera2.py` may swap red and blue (`TODO.md`); green and yellow survive that swap badly, so check it before flying this on a Raspberry Pi camera.
- Path settings, at the top of `path.py`: `PATH_SPEED_MPS = 0.3`, `PATH_HEIGHT_M = 1.5`, `LATERAL_GAIN = 0.8`, `YAW_GAIN = 1.0`, `MAX_OFFSET_M = 0.4`, `PATH_LOST_AFTER_S = 1.0`, `END_AFTER_S = 0.5`.
- The rules clear 50 cm either side of the line of obstacles. Leaving that band is a failure, not something to correct slowly: beyond `MAX_OFFSET_M` the step stops and fails.
- This is new detection, not a change to marker detection, so the ArUco benchmarks need not run.
- Branch `feature/safe-path`, log `logs/YYYY-MM-DD-feature-safe-path.md`. Run `source .venv/bin/activate` before `./scripts/check.sh`.

## Review Focus

1. **Only one line in view** (in a curve, or after drifting): the path centre is placed `LINE_GAP_M / 2` to the correct side of that line. Test `test_one_line_is_enough` (Task 1).
2. **Lines on the wrong sides:** green left and yellow right means the drone faces backwards along the path. `find_path` reports `reversed=True`, and the follower fails rather than flying toward the start. Test `test_reversed_path_is_reported` (Task 1).
3. **Other green or yellow things on the floor** (tape, a poster): blobs that are not long and thin are ignored. Test `test_blobs_are_not_lines` (Task 1).
4. **The red and white field boundary and the blue zone lines:** never taken for the path. Test `test_other_line_colours_are_ignored` (Task 1).
5. **Both lines vanish mid-path** (glare, a gap in the tape): the drone stops; after `PATH_LOST_AFTER_S` the step fails. It is only an "end" if an end marker was seen. Test `test_lost_path_is_not_the_end` (Task 2).

### Task 1: Line detection

**Files:**
- Create: `droneload/vision/lines.py`
- Test: `tests/test_lines.py`

**Interfaces:**
- Produces:

```python
@dataclass(frozen=True)
class PathView:
    offset_px: float      # path centre minus image centre, at the image's middle row; positive is right
    heading_rad: float    # path direction relative to image up; positive is clockwise
    green: bool           # each line seen this frame
    yellow: bool
    reversed: bool        # green is left of yellow
    ahead: bool           # a line reaches the top quarter of the image

def find_path(frame_bgr, gap_px) -> PathView | None      # None when neither line is seen
def line_mask(frame_bgr, hsv_range) -> np.ndarray        # the cleaned mask, for the tuning tool and the jury image
```

`gap_px` is the expected gap between the lines in pixels at the current height; the caller computes it as `LINE_GAP_M × fx / height`.

- [ ] **Step 1: Write the failing tests.** Build floors with `sim_camera.draw_line`: yellow at east 2.0 and green at east 3.0, both running north, and render from 1.5 m.

  - `test_straight_path_centred`: from east 2.5, `offset_px` is within 5 of 0, `heading_rad` within 0.03 of 0, both colours seen, `ahead` true, `reversed` false.
  - `test_offset_to_the_side`: from east 2.3, `offset_px` is `900 × 0.2 / 1.5 = 120` ± 8.
  - `test_heading`: with yaw 0.2 rad, `heading_rad` is −0.2 ± 0.04.
  - `test_one_line_is_enough`: from east 3.3, where only green is in view, `offset_px` is `900 × (−0.8) / 1.5 = −480` ± 15.
  - `test_reversed_path_is_reported`: with yaw π, `reversed` is true.
  - `test_blobs_are_not_lines`: a green 20 cm square and no lines gives `None`.
  - `test_other_line_colours_are_ignored`: red, white and blue lines only give `None`.
  - `test_end_of_lines`: rendered 0.3 m before both lines stop, `ahead` is false.
  - `test_curve`: on a quarter circle of radius 2 m, `heading_rad` has the curve's sign.

- [ ] **Step 2: Run them and check they fail.** `python -m pytest tests/test_lines.py -q`.
- [ ] **Step 3: Implement.** Threshold in HSV with `cv2.inRange`, open and close with a 5 × 5 kernel, keep contours whose `cv2.minAreaRect` is at least 6 times longer than wide, and fit each colour's points with `cv2.fitLine`.

### Task 2: Path following

**Files:**
- Create: `droneload/navigation/path.py`
- Test: `tests/test_navigation_path.py`

**Interfaces:**
- Consumes: `lines.find_path`, `Context`, `Vehicle.send_velocity`, `vehicle.height_m`, the camera's focal length from the detector's calibration.
- Produces:

```python
class PathFollower:
    def update(self, view, height_m, fx) -> tuple    # (forward_mps, right_mps, yaw_rate_rps)

class FollowPath:                                    # a step
    def __init__(self, end_marker=None, camera="down", timeout_s=120): ...
```

`update` returns `right = LATERAL_GAIN × offset_m`, `yaw_rate = YAW_GAIN × heading`, and `forward = PATH_SPEED_MPS × max(0, 1 − |heading| / 0.5)`, so the drone slows in curves. `FollowPath` finishes when `end_marker` is confirmed in view, or, with `end_marker=None`, when `ahead` has been false for `END_AFTER_S` with a line still in view.

- [ ] **Step 1: Write the failing tests,** closed loop with `KinematicVehicle`, `SimCamera` and the runner, on a floor with an S-shaped path 5 m long, as Figure 1 of the rules shows.

  - `test_follows_a_straight_path`: 4 m straight; the vehicle stays within 10 cm of the centre line and finishes at the end.
  - `test_follows_an_s_curve`: the vehicle stays within 25 cm of the centre line throughout.
  - `test_recovers_from_a_start_offset`: starting 0.3 m to one side and 20° off heading, it is within 10 cm after 3 m.
  - `test_follows_back`: started at the far end facing the start, it follows the path back and finishes when marker 0 comes into view (`FollowPath(end_marker=0)`).
  - `test_leaving_the_band_fails`: with `drift_mps` of 0.4 m/s sideways, the step fails before the vehicle is 0.5 m from the centre line.
  - `test_lost_path_is_not_the_end`: a 1.5 m gap in both lines makes the step fail, with zero velocity sent first.
  - `test_reversed_start_fails`: started facing the wrong way, the step fails within 1 s and the vehicle has moved less than 10 cm.
