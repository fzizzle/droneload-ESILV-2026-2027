# Roadmap to the Final

Written 2026-11-18, after a review of the code against the V1 rules. It orders the plans in this folder, fixes the interfaces they share and lists the decisions that need the project lead. Each plan can be built and tested on its own.

## Where the Points Are

The 670 flight points split into two missions (`docs/contest-rules.md`). Automatic take-off and landing add 20, counted once.

| | Mission 1: safe path + referee target | Mission 2: window + robot |
|---|---|---|
| Crossing | Path out and back 60, round trip 30 | Window out 30, back 50, with object up to 20, round trip 70 |
| Zone C task | Search 30, recognise 10, drop 20 | Robot follow 30, robot steps 40, search 30, recognise 10, drop 20 |
| Full mission | 100 | 100 |
| Total | 250 | 400 |

- **First target:** Part 2 alone, by the safe path with a 5 s hover in zone C, is 110 points. It needs a downward camera, line following and a landing on ArUco 0.
- **Run order at the final:** Mission 1 first, a battery swap in zone A, then Mission 2.
- **Gating rule:** no action scores unless its detections show on the organisers' screen.

## Shared Interfaces

Plans name these exactly. Change one here first, then in every plan that uses it.

**Frames.** Camera frame, as `pose.marker_offset()` returns: x right, y down, z forward along the lens. Body frame: x forward, y right, z down. Level frame: the body frame with roll and pitch removed, so x is the drone's heading on the floor. Local frame: north, east, down from the estimator's origin, as `Vehicle.position`.

**vision** (`droneload/vision/detect.py`, plan 3):

```python
@dataclass(frozen=True)
class Marker:
    id: int
    label: str
    cx: float                 # pixels, as logged today
    cy: float
    corners: np.ndarray       # shape (4, 2), pixels, OpenCV corner order
    side_px: float
    offset_m: tuple | None    # camera frame; None without a calibration

@dataclass(frozen=True)
class MarkerFrame:
    markers: list             # confirmed markers, sorted by ID
    rejected: list            # corner arrays detected but not confirmed
    detect_ms: float

class MarkerDetector:
    def __init__(self, dict_name=ARUCO_DICT, track=True, calibration=None): ...
    def process(self, frame) -> MarkerFrame: ...   # BGR or grey image

def annotate(frame, marker_frame, status="") -> np.ndarray   # the jury image
```

**flight** (`droneload/flight/vehicle.py`, plan 4), added to today's `Vehicle`:

```python
vehicle.poll()                                   # heartbeat if due, read waiting messages, never blocks
vehicle.send_velocity(forward_mps, right_mps, down_mps=0.0, yaw_rate_rps=0.0)
vehicle.stop()                                   # zero velocity
vehicle.request_mode(mode); vehicle.request_arm(); vehicle.request_takeoff(alt_m)
vehicle.attitude                                 # (roll, pitch, yaw) in radians, or None
vehicle.height_m                                 # rangefinder height, or None
vehicle.battery                                  # (volts, percent), or None
```

`testing/fake_vehicle.py` holds `KinematicVehicle`, with the same surface and a `step(dt)` method, for tests without the simulator.

**mission** (`droneload/mission/runner.py`, plan 5):

```python
@dataclass
class Context:
    vehicle: object
    cameras: dict             # "down", "forward" -> camera with read()
    detectors: dict           # same names -> MarkerDetector
    frames: dict              # same names -> latest BGR frame
    markers: dict             # same names -> latest MarkerFrame
    frame_age_s: dict         # same names -> seconds since the last new frame
    now_s: float
    confirmed: bool           # True for one tick after the operator confirms
    notes: dict               # data passed between steps, such as notes["target"]

run(steps, ctx, abort=None, clock=time.monotonic, sleep=time.sleep) -> str   # "complete", "aborted" or "pilot"
```

Later plans add fields: `posters` (plan 10) and `robot` (plan 12).

A step is any object with `name`, `timeout_s`, `start(ctx)` and `tick(ctx)`. `tick` returns `None` while running, `True` when done and `False` on failure. Steps in `navigation`, `payload` and `comms` follow this shape without importing `mission`.

**navigation** (`droneload/navigation/`, plan 6): `frames.level_offset(offset_cam, mount, roll, pitch) -> (forward_m, right_m, down_m)` with mounts `frames.DOWN_CAMERA` and `frames.FORWARD_CAMERA`, and `centre.Centring`.

**Simulated camera** (`testing/sim_camera.py`, plan 2): `Floor`, `make_floor()`, `render_down()` and `SimCamera`, which has `open()`, `read()` and `release()` like any camera.

## Decisions for the Project Lead

1. **Flight controller code.** Plans 4, 6, 7, 10, 12, 13 and 14 write code that commands a drone, in the simulator first. Plans 8, 9 and 11 add smaller pieces to `flight`: status text, a telemetry log and a relay output. `AGENTS.md` asks for a person's OK before that.
2. **Real-drone connection.** `flight` refuses anything but a local simulator. Plan 1 proposes the propellers-off bench test that should come before lifting this.
3. **Grabber.** Plan 11 recommends the electromagnets already in the box, after a drop test.
4. **Robot link.** Plan 12 needs `pyserial` and a radio pair. The previous team's HC-12 modules share the 433 MHz band with the kit's telemetry radio.
5. **Cameras and computer.** Still blocked on the Qualcomm board's model; plan 1 starts with identifying it.
6. **Marker ID filter.** Plan 15 proposes dropping IDs outside 0-9.

## Questions for the Organisers

Ask on the Droneload Discord. Each blocks a design choice.

- How does the drone learn the referee's target without a manual command? (plans 5 and 10)
- May teams use Wi-Fi at the venue, and how does video reach the organisers' screen: HDMI from a team laptop? (plan 8)
- Where exactly are the window markers, and what are the safe path's line width and spacing? (plans 7 and 14)
- Which link may the team module on the robot use? (plan 12)
- Will the floor be the black tarp or bare ground? (plans 1 and 7)

## Out of Scope

- Marvelmind positioning. The kit lends one beacon and the other four are only at the final, so it cannot be tested. The missions are designed to work on optical flow plus what the cameras see. Revisit if the organisers lend a full set.
- Gazebo. Plan 2 covers the downward camera with far less setup. Plan 14 extends it to upright surfaces for the window.
- A team-built drone (+50 bonus). The loan kit stays the assumption.
